## Implemented and tested

- `/members`: school-email OTP sign-in, scoped tasks, progress/evidence updates, group responsibilities, calendar, shared projects and private reflections.
- `/admin/member-access`: existing restricted administrator authorizes an exact email, explicit planning-person mapping, group and platform role. Authorization creates a native Supabase Auth identity and a seven-day invitation, **without sending email**. Invitation renewal requires email verification again. No account mapping is inferred from names.
- `/members/access`: authenticated platform admins can manage authorizations and roles. Coordinators cannot manage accounts. Existing `/admin` case records and confidential photos remain separately protected by the original core-admin session; a platform admin is not automatically a confidential-case administrator.
- Native Supabase Auth verifies email codes; SSR cookies are httpOnly, Secure in production and SameSite. No service key or session token is passed through client props or localStorage. Server identity checks call `getUser`, then read current active membership; user-editable JWT metadata never grants roles.
- Exact-origin JSON mutations protect against cross-site requests. OTP requests/verification and member writes use durable database rate limits. Uninvited school-email requests receive generic responses and no email.
- RLS SELECT policies enforce own-task/group scopes. Authenticated users cannot directly change table rows or role records. Narrow database RPCs derive identity from `auth.uid()`, check live membership, serialize edits, and advance the same master revision used by admin editing. Conflicts return 409. Cross-group/unassigned-task attacks and forged payload fields are rejected.
- Task changes, reflections and their audit entries are transactional. Exact same-author/same-day reflection retries are deduplicated. Member projections exclude original conflict notes, evidence records, initial interest name lists and emails. Members receive no uploads or case-management capability.
- Two independent release gates: `MEMBERS_ENABLED=true` in the app and `member_settings.enabled=true` in the database. Both default closed.

## Rollback / emergency stop

Set app `MEMBERS_ENABLED=false` and database `member_settings.enabled=false`. The database switch blocks existing tokens' RLS and mutation RPC access, independently of deployment timing. Preserve data/audit records for investigation; do not drop tables. Restore the previous deployment if needed. Existing public site and sewing workflow do not depend on member gates.
